# Spec：后台作业与完成回报（2026-11-08）

所属功能 ADR：[ADR-0024](adr/background-jobs/0024-long-running-jobs.md)。本 spec 只覆盖本次开发部分。

## 用户目标

对 Bot 说一句需要很久才能做完的事（下载、拉依赖、构建），Bot 立刻回一句"已派发 <jobId>"，然后**继续能接下一句**；活儿在后台跑完，控制台时间线上落一条通知并亮未读徽标，操作者回来一眼看见结果。想知道细节或同时有好几个活儿，问一句，Bot 用 `job.list` / `job.status` 给出事实，也可以取消。

## 本次范围

**做：**

- 命令型作业（一次 bash 执行），死因是时长或带宽，不需要模型多轮参与。
- 每个作业一个独立工作目录，作业之间、作业与前台命令之间不共享写入目标。
- 作业状态索引表 + 模型侧查询／取消工具 + 控制台作业面与未读提示。
- 完成后由宿主落一行确定性通知（命令、退出码、耗时、输出尾）。通知不经过模型，也没有无请求的生成路径。

**不做（本次排除，不构成长期禁令）：**

- 含模型多轮的作业（"跑完测试再帮我改"）。它需要先定死前台请求与后台作业的模型侧串行规则，留作后续 spec。
- 由模型在完成时开口（无请求的生成路径）。本次通知由宿主直接落盘；模型说明结果发生在下一次交互。定时唤醒等于重建 ADR-0022 已废弃的调度器。
- 出站通知通道（webhook／邮件）。本次通知只在控制台内。
- 进度百分比／实时输出流。作业面本次只给状态与终态摘要。
- 作业的失败重试策略（自动重发）。本次只记录失败与 `unknown`，重试由人或模型显式发起。

## 相关接口与状态

### 状态归属（新增两行，与既有三行并存）

| 所有者 | 状态职责 |
| --- | --- |
| 作业层 | 作业的排队、运行、终态；作业自己的工作记录与工作目录 |
| 通知层 | 已落盘的通知、已读／未读；本次不做发送进度与发送确认 |

### 索引表 `background_jobs`

| 列 | 语义 |
| --- | --- |
| `jobId` | `job:<botId>:<uuid>`，宿主生成，重试时保持稳定 |
| `botId` | 归属；所有查询按它过滤 |
| `conversationId` | 派发它的会话，通知按此归属到时间线 |
| `taskId` | 底座任务标识，终态真相的入口 |
| `kind` | 本次只有 `command`；旧行按未知值处理，不猜测 |
| `command` | 展示用的命令原文（按显示上限截断） |
| `state` | `queued` / `running` / `done` / `failed` / `canceled` / `unknown` |
| `exitCode` | 仅终态有值 |
| `error` | 业务失败码；与执行失败区分 |
| `createdAt` / `startedAt` / `finishedAt` | ISO 8601 UTC；未发生的为 null |

`state` 是索引，不是权威：与 `harness.getTask(taskId)` 不一致时以底座为准，并把差异记为 `unknown` 而不是猜一个终态。

### 通知表 `notices`

| 列 | 语义 |
| --- | --- |
| `noticeId` | 宿主生成 |
| `botId` / `jobId` | 归属与来源作业，`jobId` 唯一 |
| `text` | 宿主写的确定性通知文本（命令、退出码、耗时、输出尾） |
| `createdAt` | 落盘时间 |
| `readAt` | null 表示未读 |

`jobId` 唯一即幂等键：作业进入终态时写一次，重启后重放同一终态不会写出第二条。

`inbox` 的含义保持严格："操作者请求"。作业通知不进 `inbox`，通知也不是回复。

### 模型侧工具

| 工具 | 参数 | 语义 |
| --- | --- | --- |
| `job.start` | `command`（必填） | 派发一个作业，立即返回 `jobId`；不等待 |
| `job.list` | 无 | 本 bot 的作业索引（状态、命令摘要、终态） |
| `job.status` | `jobId` | 单个作业的状态与终态摘要 |
| `job.cancel` | `jobId` | 请求取消；返回是否已标记 |

**没有 `job.wait`。** 等待等于把请求重新挂住，退回 300 秒陷阱。

### 命名消歧（实施第一步）

`src/inbox.ts:14` 已有 `export interface Job extends TextRequest`，指的是"操作者请求"；`src/bot-manager.ts` 里 `job` 局部变量也指同一物。本功能的"作业"是另一个概念，不能混用。第一步把 `inbox.Job` 重命名为 `InboxRequest`（纯重命名，无行为变化），再引入作业命名。

## 副作用和授权

- 工具参数只表达意图：`job.start` 只收 `command`。工作目录、环境、执行主机、凭据、命令时长上限全部由宿主从 bot 身份与配置派生，不接受模型给的路径、环境变量或秒数——超时上限是资源边界，不是任务意图。
- 作业工具的可见范围按 botId 过滤，模型不能借 `jobId` 读或取消别的 bot 的作业。
- `job.cancel` 是取消请求，不是撤销已发生的副作用。契约沿用：已经提交的外部副作用仍可能发生，取消确认的是执行终态。
- 派发作业消耗执行机并发槽位（上限见下），这是一次真实的资源占用，不是排队提示。
- 作业的命令时长上限由宿主取 `EXECUTION_MAX_TIMEOUT_SECONDS`（默认 3600，`src/config.ts:351`），再按线路派生封顶（RPC 下为 3,540,000 ms，`src/execution/rpc-protocol.ts:22,41,652`）。作业不受 300 秒请求预算约束，但**必须有上限**，超限是作业失败，不是进程失控。

## 资源与失败恢复边界

- **并发**：共享执行主机的 `EXECUTION_AGENT_MAX_CONCURRENT` 显式设为 4（现行 runbook 值为 3，一并同步 `docs/runbook-shared-execution-host.md:88`）。每 bot 同时最多 1 个写型作业，因此作业占 1 槽、前台命令留 3 槽。超限返回 `busy` + `not_started`（`src/execution/rpc-server.ts:448-449`）：**未执行、可安全重试**，工具必须把它作为可重试业务错误返回，不能报成执行失败。
- **重启**：作业任务不设 `abandonOnRestart`，跨进程重启继续跑。重启后 `running` 的索引行必须与 `getTask` 核对；不一致时以底座为准。
- **通知落盘**：作业进入终态时由宿主写一行通知，`notices.jobId` 唯一。重启后核对 `running` 索引行时若发现任务已是终态，补写通知走同一条 upsert，因此同一次完成不会产生两条通知。落通知不经过模型，也不占用生成预算。
- **半截外部操作**：作业被取消或进程被杀时，执行机磁盘上可能留下残骸（进程组终止是文档化行为，`docs/mvp-verification.md:77`）。结果未知记为 `unknown`，不得记为未执行。命令是否可续（`curl -C -`、`rsync --partial`）决定重试是否安全，实施时按命令类型区分，不默认重试。
- **删除 bot**：`background_jobs` 与 `notices` 必须纳入 `src/inbox.ts:441` 的清账路径，并计入删除报告的计数，否则删除不再是真实擦除。

## 实施步骤

1. `inbox.Job` → `InboxRequest` 重命名。
2. 契约修订：`docs/contracts-and-lifecycle.md` 的状态归属表新增作业层与通知层；`步骤 5`（`:160`）与 `:174` 段落改为容纳"回复不是唯一出口"。
3. 迁移：`background_jobs` 与 `notices` 两表，沿用既有 `CREATE TABLE IF NOT EXISTS` + `addColumn` 惯例。
4. 作业任务定义：照 `src/memory/archive-task.ts` 的 `phases` + `abort` 形态，`{ background: true }`，不设 `abandonOnRestart`。
5. 四个作业工具（`job.start` / `job.list` / `job.status` / `job.cancel`）。
6. 作业终态由宿主落一行确定性通知（`notices.jobId` 唯一），不经模型。
7. 控制台：作业面、未读徽标、时间线里的通知。
8. 删除路径接入 `background_jobs` / `notices`。
9. 配置：共享执行主机并发值 3 → 4，同步 runbook。

## 可检查的验收条件

1. 一条超过 300 秒的命令：请求在 300 秒内返回"已派发"，作业继续运行，完成后控制台时间线出现一条通知并亮未读徽标；操作者下次问起时，Bot 用 `job.status` 说明结果。
2. 作业运行期间再发一条请求：该请求在 300 秒内得到回复，作业不受影响（对应 README:574 的 "does not keep the parent busy"）。
3. 作业运行期间重启进程：任务跨重启继续被调度；**已经被交给执行环境的命令不重放**，该作业以 `unknown` + `JOB_INTERRUPTED` 收尾并如实写入索引与通知（进程被杀时副作用可能已经发生，重放不安全）；未开始执行的作业照常跑完。索引状态与 `getTask` 一致；终态只产生一条通知。
4. 作业被取消：abort 协议提交终态，已发生的副作用不被谎报为未发生。
5. 执行机并发超限：工具返回可重试的业务错误（`not_started`），不是执行失败。
6. 删除 bot：该 bot 的作业行与通知行被清除，并计入删除报告。
